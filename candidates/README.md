# Candidates: цвет вина и винодельня по фото

`solution/v1/predictor.py` предоставляет единственный интерфейс решения:
`predict(image_path) -> {category, brand, _status, _error, _trace}`. Runner знает
только имя версии и этот вызов. Prompt, модель, routing, timeout и параметры
генерации живут в `solution/v1/prompt.txt` и `solution/v1/config.json`; новая
версия может быть добавлена соседней папкой с собственным `predictor.py`.
`candidates.match.match_products(prediction)` возвращает все подходящие
карточки Каталога: фильтрует по обоим известным полям или по одному известному;
при двух отказах возвращает пустой список. Порядок карточек — порядок Каталога,
не рейтинг похожести.

Значения для закрытых списков загружаются из `data/strapi/catalog_dataset.csv`
через CSV-парсер: четыре значения `Категория` и 135 значений `Винодельня`.
Пустой ответ для каждого поля: `Не удалось определить`. Успешный ответ имеет
`_status: "ok"`; сетевые и форматные ошибки имеют отдельные статусы. В `_trace`
хранится сырой ответ API, но не base64 изображения и не ключ API.

## Данные

`dataset.jsonl` содержит 20 примеров из `data/test`. Выборка воспроизводима:
`random.Random(20260923)` выбирает 20 различных папок из 65 (сортировка по
пути), затем по одному файлу в каждой. Исходно было 76 файлов. Изображения
просмотрены вручную; метки `category` и `brand` сверены по точному `Slug`
соответствующей папки в Каталоге. Хеш файла защищает набор от тихой замены.
Эта случайная выборка не содержит оранжевого вина. Метка винодельни означает
истинное значение Каталога, даже когда на лицевой этикетке видна только линейка
(`Di Caspico`, `Desono`, `Penpalo`, `Cantiani`, `Cuvée №2`). Поэтому точность
бренда здесь оценивает восстановление канонической винодельни, а не только
чтение напечатанного названия. Набор мал и не оценивает точность поиска товара.

## Запуск

Из корня репозитория, с Python из `.venv` и `OPENROUTER_API_KEY` в окружении
или `.env`:

```powershell
.venv/Scripts/python.exe -m candidates.run --solution v1
.venv/Scripts/python.exe -m candidates.eval candidates/results/v1_<timestamp>
```

Первый вызов выполняет по одному запросу на фото, без ретраев, и сразу считает
метрики. `--limit N` полезен для smoke-прогона; остальные случаи считаются
пропущенными в метриках. Каждый прогон создаёт новую папку в `results/` с
`run.json` (хеши dataset и файлов решения), `predictions.jsonl` (сырые ответы,
ошибки и latency каждой попытки), `metrics.json` (точность категории, бренда и
пары, частота отказов, доля исходных slug в пуле, размер пула, статусы и latency
p50/p95). Второй вызов пересчитывает
метрики без обращения к модели. Файлы `data/test` и Каталог не меняются.
Итоговые результаты первого полного прогона кратко описаны в `results/README.md`.

Параметр `reasoning.effort` в `v1/config.json` закреплён как `none`: этот вариант
решения намеренно не допускает reasoning. Для модели, работающей только через
другого провайдера, можно изменить `provider` и `model` в config либо создать
новую версию решения.
