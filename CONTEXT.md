# vinishko — контекст проекта для продолжения в Claude Code

Свёртка диалога по проектированию сканера российских вин по фото. Всё ниже — принятые решения, состояние данных и план. Читать целиком перед началом работы.

## 1. Кейс

Хакатон РСХБ, кейс «Сканер российских вин с описанием на платформе „Своё вино"». Полное ТЗ — `10__РСХБ_Цифра.pdf`.

Суть: по фото бутылки/этикетки с телефона найти карточку вина в каталоге платформы и вернуть `{"slug": "..."}`.

Ключевые требования из ТЗ:
- Каталог 1500–2000 позиций, **по одному студийному фото на позицию**.
- Организатор прямо пишет: главный источник ошибок — **near-duplicates** (одна этикетка, разные год/сезон/категория/крепость), и приватный тест проверяет именно их.
- Целевая точность 90–100% top-1 на приватном тесте (полевые фото: полка, угол, блики, плохой свет).
- SLA ответа ≤ 3 с. Демо локально на своём железе; GPU может не быть у жюри.
- Нужен confidence для top-1 и top-5 в API; обработка «вина нет в каталоге» (честный отказ или похожие — оценивается особенно высоко).
- OCR допустим, но не обязателен; CV-компонент обязателен.
- Рекомендованный стек: Nuxt, PostgreSQL + pgvector, SigLIP 2, Strapi, Docker.
- Оценка: достоверность выдачи 50/100, функция после поиска 20, архитектура 15, дизайн 10, скорость 5.
- Скрипт кейсодержателя шлёт фото по одному, ждёт плоский JSON со slug.

## 2. Данные каталога

Дамп Strapi: `strapi_output0709.csv` (4147 строк, каждая продублирована 2 раза) → после чистки `datasets/hack/strapi_clean.csv` (2045 строк, колонка `filename` указывает на оригинал в `strapi/uploads`). Неразрешённые 52 + 6 строк — в `strapi_unresolved.csv`.

Фото: `prod-svoe-vino-strapi/prod-svoe-vino/strapi/uploads`, 15803 файла = ~6200 оригиналов + Strapi-превью (`thumbnail_`, `small_`, `medium_`, `large_` — игнорировать). Каталогом покрыто 2188 оригиналов; ~4000 остальных — фото виноделен, новостей, сгенерированные картинки. Многие оригиналы крошечные: ~140×600 px.

Качество: скрейп + ручной ввод без валидации. Найдены ошибки: чужие фото под slug (Agora Cabernet ↔ Sauvignon), дубли сущностей (`kokur-2025` / `kokur-suhoe-2025`), вырожденные slug (`wine`, `merlo-1`), ненормализованный цвет, 4 категории на всё.

### Структура slug

Slug — ответ системы и метка класса. Две популяции:

- **Спарсенная часть (1453):** `{винодельня}-{название}-{сорта}-{цвет}-{сахар}-{крепость}`. Цвет ∈ krasnoe/beloe/rozovoe/oranzhevoe; сахар ∈ suhoe/polusuhoe/polusladkoe/sladkoe/bryut/ekstra-bryut; крепость без точки: `12`=12%, `125`=12.5%, иногда диапазон `105-125`.
- **Ручная часть (592):** произвольно — название+год (`aligote-barrel-2024`), суффиксы `-1`, вырожденные. Год есть у 77.

Различающие поля (все присутствуют на этикетке текстом): винодельня, название, сорт, цвет, сахар, крепость, год.

### Near-duplicates (посчитано)

84 группы, 183 slug, в основном пары. Три типа:
1. Только крепость (85 slug): `...-bryut-12` vs `...-bryut-125`. Визуально неразличимы. Только OCR крепости.
2. Серия с разными сортами/сахаром: «Солнце, воздух, виноград» ×5, «Par Amour» ×4. Дизайн общий, различие в цвете и словах.
3. Одно фото на два slug (9 пар): `aligote-barrel-2024/2025`, `kokur-2025/kokur-suhoe-2025`, `cantiani-riesling/-1`. Retrieval не различит в принципе → **спросить организаторов**, какой slug верный / есть ли в тесте.

Разбор всех slug на поля + номера групп: `catalog_parsed_groups.csv` (колонки: Slug, Название, Винодельня, Категория, Сорт, slug_style, slug_color, slug_sweet, slug_abv, year, dup_group, dup_group_size, filename).

### Публичный тест

3 фото в `queries/`: полка, телефон. Из трёх вин в каталоге только «Мускатель белый» Массандры; «Aristov Donum XXIV» и «Табия Пино Нуар» отсутствуют → приватный тест почти наверняка содержит вина не из каталога. Отказ надо делать честно.

## 3. Архитектура (принято)

Двухуровневый поиск. **Уровень 1** — визуальный retrieval до **группы** (серии одинакового дизайна). **Уровень 2** — целевая проверка различающих признаков внутри группы.

Семь компонентов:

1. **Детектор/нормализация.** Роутер сцены (бутылка/полка/бокал/винная карта/кроп). Детекция бутылки open-vocab (OWLv2 / YOLO-World / Grounding DINO, zero-shot) + SAM-маска. Нормализация: EXIF, прозрачный фон → белая подложка до RGB (каталожные вырезки почти все RGBA с чёрным под альфой; правило 2026-09-27, живёт в `seg.open_image`) → PCA по маске даёт ось бутылки, знак — по профилю ширины (узкий конец = верх) → поворот до вертикали → bbox с отступом 5–10% → фон вне маски **заглушается** по растушёванной альфе: по умолчанию заливка серым `[124, 116, 104]` — среднее нормализации ImageNet, на входе энкодера это нули, фон становится одинаковым у запроса и у каталога на белом; размытие оригинала осталось опцией `background.mode=blur` для абляции. Кроп — **окно вокруг основной этикетки** в системе координат бутылки: по ширине вся бутылка, по высоте этикетка с запасом 20% её высоты вверх и вниз, не дальше маски бутылки (`crop.padding_y` в normalize.toml); по ширине не режем, разрыв с WineSensed есть только по высоте. Решение 2026-09-19, отменяет прежнее «кроп по всей бутылке»: WineSensed — крупные планы, где видна половина бутылки, а на инференсе бутылки целые, и этикетка в кропе всей бутылки выходила втрое мельче, чем в трейне. В окне этикетка занимает около 70% высоты и у целой бутылки, и у крупного плана; часть стекла, плечи и низ корпуса в окне остаются. Для абляции «вся бутылка» — большой `crop.padding_y`: окно упирается в маску со всех сторон. Вырезка этикетки впритык — только для OCR/верификации/винтажа. Если виден короткий обрубок (aspect < 2), ось PCA неустойчива — кроп без поворота, фон заливается как обычно. Выход шага — `list[BottleCrop | RejectedBottle]`: годная бутылка — целевая с читаемой основной этикеткой, внутри готовый кроп для энкодера; остальные уходят отказами с причиной и маской для интерфейса, целое фото как запасной вариант не отдаётся. Общие структуры пайплайна — `vinishko/pipeline/structs.py` (решение 2026-09-26, отменяет `Sample`, который шаги дописывали): шаги не знают друг о друге и общего изменяемого объекта нет, их выходы связывает оркестратор `vinishko/pipeline/pipeline.py` — поиск получает `list[BottleCrop]`, реранкер `list[BottleCandidates | UnmatchedBottle]` с кропом внутри; поздний отказ — `BottleCrop.reject` и замена в разметке по `uuid`; причины отказа у каждого шага свои, наследник `structs.Reason`.
2. **Энкодер + индекс.** DINOv3 ViT-B/16 (`facebook/dinov3-vitb16-pretrain-lvd1689m`), прямоугольный вход с сохранением пропорций (например 640–768 по высоте, кратно 16, RoPE это позволяет). Пулинг — **CLS** (принято без абляции; GeM/CLS⊕GeM — потом, пулинг вынести в отдельную функцию `tokens → vector`). Индекс: qdrant, метрика косинус, точка на позицию каталога с метаданными `slug`, `group`, `group_slugs`, имя кропа, поля каталога, модель и ревизия (решение 2026-09-26, вместо pgvector; модуль `vinishko/pipeline/steps/vis_searcher`, сборка коллекции — `build_catalog`, обученная модель тянется с Hugging Face `pomelk1n/qwopus-twinturbo-gguf-umer-vitl16-512`; на CUDA TensorRT bf16, на CPU OpenVINO). **Скор группы = max по её векторам**, никаких центроидов; режимы выдачи `top_n` и `groups`, см. README модуля. Мультивектор на SKU (каталожный + прототипы с полевых фото) — позже.
3. **Геометрическая верификация** на top-K: ALIKED + LightGlue + MAGSAC++, гомография по развёрнутой этикетке. Лицензии: ALIKED BSD-3, LightGlue Apache; **SuperPoint не брать** (некоммерческая). Выход — признаки (инлаеры, доля, ошибка репроекции, sanity гомографии) + гомография. **Ничего не отбрасывает** — решает фьюзер. Дескрипторы галереи считать лениво для top-K с кешем.
4. **OCR + текстовый матч.** VLM (Qwen3-VL) со schema-JSON: винодельня, название, сорт, цвет, сахар, крепость, год. Constrained decoding по году/крепости, self-consistency ×3, поле unknown при расхождении. Кириллица — плюс, не минус (каталог на русском, матчить с «Название вина», не со slug). Вызывать только когда уровень 1 не дал уверенности. Внутри группы сравнивать **поле с полем** (числа численно, сахар/сорт по словарю), Левенштейн/RapidFuzz — только для винодельни/названия, не для тайбрейка. Стоп-лист служебного текста.
5. **Фьюзер.** Сейчас — правила: retrieval → группа → один член = ответ; несколько → OCR-поля + вторые ручки → член с максимумом совпавших сигналов; ничья → приор (slug без `-1`, спарсенный > ручной, свежий год). Позже, при наличии полевых фото, — логрегрессия на 5 признаках с CV. Один порог на всю систему, режимы accept / top-3 / reject. Confidence в API — отрыв косинуса top-1 от top-2 + инлаеры.
6. **Вторые ручки внутри группы** (кроме OCR): цвет вина/стекла (белое/красное/розовое — тривиальный классификатор на кропе бутылки), word spotting шаблоном различающего слова из эталона (если эталон достаточного разрешения), классификатор цифр на вырезанной зоне года/крепости, zero-shot SigLIP 2 текст-к-картинке по названиям членов группы, форма бутылки/капсула. Каждый сигнал даёт очки, отсутствие сигнала = 0, не штраф.
7. **Логи** выбора пользователя → полевые пары для дообучения, разметка фьюзера, прототипы в индекс.

Сервинг двухъярусный: энкодер всегда (десятки мс), верификация на top-K (сотни мс), OCR — только при неуверенности (секунды).

### Сборка групп (автоматически, union-find)

Четыре правила связывания: (1) один pHash картинки; (2) одна винодельня + нормализованное название (lower, без пунктуации, года, слов сахара/цвета); (3) один стем slug без хвоста крепости и `-N`; (4) визуально идентичные эталоны (косинус > порог **и** верификация с высокой долей инлаеров; порог калибруется по парам с одинаковым файлом vs случайным). Для группы хранить набор **различающих полей** — инструкция уровню 2. Группы без различающих полей и с противоречием «одно фото, разные поля» — в очередь на проверку (порядка 10–20 случаев). Инкрементально: новая позиция прогоняется через правила. Подавать как «модуль гигиены каталога», не как «нужен эксперт».

## 4. Обучение энкодера (принято)

Учить энкодер — решено, это основной путь.

- Инициализация: DINOv3 ViT-B/16. L — только если frozen-абляция покажет ≥3 п. преимущества; тогда L замороженный + обучаемая голова.
- Голова: `BN → Linear(768, 512, bias=True) → BN → L2`, Linear инициализирован из PCA-whitening на замороженных фичах (W = Λ^{-1/2}Uᵀ с регуляризацией λ^{-0.25} или +ε, b = −Wμ). Bias нужен из-за L2: центрирование разворачивает конус на сферу.
- Лосс: **sub-center ArcFace** (K=3) + **динамический margin** по размеру класса: `m_c = 0.5 · n_c^{-0.25} + 0.05`, `s = 30`. Sub-center — под многомодальность (редизайны, серии) и шум меток. Код лосса был написан в диалоге (SubCenterArcFace с `cos.view(B,-1,k).max(2)`, margins из class_counts).
- Классы: WineSensed — id вина **без винтажа**; Products-10K — SKU; SOP/RP2K — связные компоненты по qrels (или колонка id товара, если есть); каталог — `dup_group`, **не slug**. Общее пространство классов со смещёнными диапазонами. ~150–300k классов → полный FC ок на одной GPU, PartialFC не нужен до ~1M.
- Сэмплер P×K; одиночные классы не выкидывать (аугментированные виды как позитивы).
- Аугментации: перспектива, поворот ±10–15°, блики, блюр, JPEG, фон полки; для каталога — синтетические виды с эталона. С вероятностью ~0.2 подавать bbox без заглушения фона.
- Нормализацию **сохранять как разметку** (маска RLE/PNG, bbox, угол, флаг знака), в даталоадере применять с джиттером (bbox ±10%, сдвиг ±5%, поворот ±10°, вариация растушёвки/заливки). Амплитуды джиттера — по замеренной ошибке SAM на полевых фото. На инференсе и для индекса — детерминированно.
- Curriculum: голова на замороженном бэкбоне (синтетика) → разморозка верхних блоков → полный FT на полевых → hard negatives по иерархии каталога (другой винтаж того же вина, другое кюве того же производителя, тот же апелласьон) → дистилляция в S/B при необходимости.
- Сейчас: учить на текущей нормализации-заглушке (open-vocab bbox + EXIF) параллельно с тем, как коллега делает SAM-пайплайн; препроцессинг — подменяемая функция. **Переобучение под финальную нормализацию обязательно**: индекс, запросы и трейн через одну функцию.


Дополнения 2026-09-25/26 (см. `vis_seacher_training/README.md`):
- Валидация пишет в TensorBoard сетку промахов `misses/oneshot_noisy` (`eval.log_misses`, по умолчанию 5): запрос, фото класса из галереи с рангом, top-5 с косинусами. По ней видно, что заметная часть промахов — шум разметки WineSensed: чужие фото под одним vivino id и дубли классов по винтажам, потолок recall@1 ≈ 0.97. Следующий круг обучения — только после чистки train обученной моделью (порог косинуса к доминантному субцентру, слияние дублей).
- Weight decay: под FSDP1 с `use_orig_params` параметры вне forward — одномерные куски шардов, поэтому правило «ndim ≤ 1 → без decay» оставляло весь бэкбон без decay в обоих серверных прогонах (эффект ≈1% сжатия за прогон при lr 1e-5). Теперь решение только по подстрокам имён `NO_DECAY_KEYWORDS`, формы тензоров не смотрятся никогда. `from_pretrained` создаёт параметры заново и снимает заморозку `mask_token` — `build_model` замораживает его повторно.
- Выбор модели по `reports/`: dino-512 (`weights/dinov3_vitl16_512`, на HF `pomelk1n/qwopus-twinturbo-gguf-umer-vitl16-512`) — norm/oneshot recall@1 90.8%, принято при FPR 1% 56%; dino-1024 (продолжение с расширенной головой, `…-vitl16-1024`) в пределах ±0.3 пп при вдвое длиннее векторе — не берём. Обе заметно лучше TULIP и EVIE (loo/norm recall@1 95.5% против 93.5% и 94.5%, принято при FPR 1% 65.7% против 50.3% и 43.0%). В oneshot отрыв top-1 от top-2 даёт AUROC 91.7% против 56% в loo — рабочий признак confidence для фьюзера.

Размещение на диске: 60 ГБ минимум, 100 ГБ комфортно (parquet + распаковка + синтетика + чекпоинты).

## 6. Eval и калибровка отказа

- Полевых фото пока нет. Собрать самим: 150–500 фото в магазинах (Перекрёсток, Лента, К&Б, Винлаб), страты: фронтально/полка/блик/два соседних винтажа одного вина, **плюс вина не из каталога** (негативы для порога).
- Метрика: precision при фиксированном coverage; отдельно на уровне кюве/группы и с винтажем. Три числа по одному визуалу: правильная группа в top-1 / top-5 / top-20.
- Дистракторы для порога «не найдено»: лучшие — российские вина не из каталога с той же полки; второй эшелон — выборка из WineSensed (отфильтровать пересечения с каталогом по винодельне). Негативы — запросы, не галерея. Процедура: гистограммы top-1 косинуса, отрыва, инлаеров для позитивов и негативов → порог под целевой FPR.
- Протокол eval фиксируется и не меняется между итерациями нормализации/обучения.
- Абляции, которые не делать на бумаге: целое фото vs кроп бутылки vs кроп этикетки; маска vs bbox; заливка константой vs размытием; CLS vs GeM; frozen B vs L.

## 7. Приоритеты на хаке

Порядок: каталог + группы → детектор zero-shot + frozen DINOv3 + индекс + прогон на 3 публичных query → полевые фото + честная метрика → OCR внутри групп → правила фьюжна → верификация на top-10 → обучение энкодера → цвет вина и прочие ручки → дистилляция при необходимости.

Не делать: штрих-код (нет базы EAN→вино), полный ArcFace с нуля до появления eval, обучаемый деварпер (множитель на верификацию, которой ещё нет), обучаемый фьюзер на 2k эталонах (это галерея, не трейн).

Про Vivino: там retrieval + ABBYY OCR для винных карт, винтаж выбирает сам пользователь. У нас такой опции нет — скрипт хочет один slug.

## 8. Репозиторий и код

Раскладка: `src/vinishko/{data,eda,index,...}`, разовые CLI-скрипты — в `scripts/`. Скачивание и разворот датасетов — `scripts/prepare_datasets.py`, разметка нормализации по датасету — `scripts/normalize_dataset.py`. Аналитика каталога — `match2.py`, `matched.pkl`, `make_clean.py` в scratchpad.

Стек: uv, Python 3.13/3.14, pandas, pillow, httpx, rich, rich-click, huggingface_hub. DINOv3 gated на HF — доступ получен, нужен `huggingface-cli login`.

Пайплайн: `vinishko/pipeline/{structs,pipeline,device,debug}.py`, шаги в `vinishko/pipeline/steps/<шаг>/` со своим конфигом рядом с модулем (`normalization/normalize.toml`, `vis_searcher/config.yaml`), README в каждой директории. Конструкторы шагов без аргументов берут конфиг рядом: `Normalizer()`, `VisSearcher()`, `Pipeline()`.

Правила кода (жёсткие):
- Импорты на верхнем уровне, **никаких try/except вокруг импортов**, никаких fallback и «красивых» re-raise.
- **Никаких пояснительных скобок в коде** вида «(реальные данные)», «(как в проде)». Комментарии только содержательные.
- Длинные строки (промпты, системные сообщения) в переписываемом коде заменять плейсхолдерами.
- Ответы по-русски, предметно, без фамильярности.

## 10. Пайплайн: структуры, поиск, устройства (состояние на 2026-09-26)

**Структуры `vinishko/pipeline/structs.py` (решение 2026-09-26, отменяет `Sample`).** Общего изменяемого объекта нет, шаги друг о друге не знают, их выходы связывает оркестратор.
- `BottleCrop` — годная бутылка с двумя кропами (решение 2026-09-27): `crop` после `render_bottle` — окно этикетки с залитым фоном, `box_crop` после `render_bottle_box` — вся бутылка по bbox повёрнутой маски с запасом `[bottle_crop]` (padding_x 0.15, padding_y 0.04, max_height 1600), фон не тронут. Вход визуального энкодера выбирается через `encoder_input`: `crop` для DINO, `box_crop` для TULIP; NDR получает `box_crop`, как и изображения позиций из каталога (`Candidate.image`). `crop_info`/`box_info` с матрицами, маски, угол, `uuid`; `markup()` — разметка без кропа для `normalization.jsonl`, формат файла не менялся. `RejectedBottle` — бутылка без ответа: от нормализации либо от позднего шага через `BottleCrop.reject(reason, detail)` с тем же `uuid`. Причины отказа у каждого шага свои, наследник `Reason` (`NormalizationReason`, `SearchReason`).
- Поиск: `Candidate` (slug, score, картинка позиции из коллекции для второго уровня, ссылка на `BottleCrop`, group, retrieved, payload) и ровно один ответ на кроп — `BottleCandidates(crop, candidates)` с непустым списком либо `UnmatchedBottle(crop, rejected)`; алиаса нет, в аннотациях `BottleCandidates | UnmatchedBottle`. Датаклассы со `slots=True`.

**Оркестратор `vinishko/pipeline/pipeline.py`.** `Pipeline(normalizer=None, searcher=None, reranker=None)`; без нормализатора поднимает `Normalizer()`. `PipelineResult(normalization, search, timings)`: `items` — итоговая разметка, где бутылка без ответа поиска стоит `RejectedBottle` с причиной поиска, `crops` — оставшиеся годными. Отладочный CLI `python -m vinishko.pipeline.debug <фото> -o <dir>` раскладывает выходы шагов: `<dir>/<имя>/normalization/` — кропы, маски, json и `markup.json` со всеми бутылками и причинами; `search/` — формат `debug_path`; `result.json` — итог по бутылкам и время шагов; старая директория удаляется; `--no-search`.

**Нормализация.** `Normalizer()` без аргументов: `normalize.toml` рядом. Устройство — `segmentation.device` (`auto` | `cpu` | `cuda:N`), переменная `NORMALIZER_DEV` перекрывает; SAM3 на CPU во float, half там падает в NMS torchvision, и в разы медленнее. `scripts/normalize_dataset.py` раздаёт карты воркерам через `CUDA_VISIBLE_DEVICES` и рассчитывает на `auto`.

**Визуальный поиск `vinishko/pipeline/steps/vis_searcher` (написан 2026-09-26).**
- `config.yaml` рядом с модулем (pydantic, опечатка в ключе — ошибка) — один источник правды и для поиска, и для сборки коллекции: `model` (репозиторий HF с экспортом: `config.json`, `preprocess.json`, `model.onnx`, `model.bf16.onnx`) и `revision`, `device`, `batch_size`, `top_k`, `qdrant` (host/port либо `path` — встроенный qdrant для отладки, `collection`), `search.mode` = `top_n` (`cosine_threshold`) | `groups` (`top_groups`, `group_threshold`), `images.kind` = `local` (`dir`) | `s3` (`endpoint`, `bucket`, `prefix`; boto3, реквизиты из окружения или `~/.aws`, кэш `cache_dir/images`), `cache_dir` (`~/.cache/vino`), `debug_path`.
- Устройство и бэкенд: `VIS_SEARCHER_DEV` перекрывает `device`; общий резолвер `vinishko/pipeline/device.py`, приоритет аргумент → переменная → конфиг → `auto` (cuda:0 при CUDA); перекрытие и выбор `auto` логируются; нет карты или пакета — ошибка, не откат. CUDA ⇒ TensorRT (сеть strongly typed, bf16-граф на Ampere и новее, иначе fp32; engine на 3080 ~26 с, кэш `cache_dir/engines/<repo>/<revision>/`), CPU ⇒ OpenVINO fp32 (~0.9 с на картинку, opset-23 граф читает, косинус с onnxruntime 1.0). Раннеры в `backends.py`, сюда переехал `vis_seacher_training/trt.py`; onnxruntime в поиске не используется.
- Модель с HF: сначала `config.json` и `preprocess.json` (контракт входа: `input_size` 512×512, `pad_color` [124, 116, 104], имя bf16-графа), сам граф докачивается после дешёвых проверок. `Preprocess` бит в бит совпадает с путём обучения: вписать с сохранением пропорций (area при уменьшении, cubic при увеличении), поля цветом заливки по центру, float32 0…255, нормировка ImageNet внутри графа.
- Коллекция qdrant (`docker-compose.yml`: qdrant v1.17 на 127.0.0.1:6333): метрика косинус, id точки = uuid5(slug), payload: `slug`, `group`, `group_slugs` (только позиции, попавшие в коллекцию), `image` (`<slug>.jpg` в хранилище), `source_image`, поля каталога `name`, `winery`, `category`, `color`, `region`, `grape`, `vintage`, `abv`, `sugar`, `sparkling`, `bottle_score`, `bottle_angle`, `model`, `model_revision`, `input_size`, `precision`, `built_at`.
