# NDR: v4 против v2 на обновлённом датасете

Дата анализа: 2026-09-20.

## Краткий вывод

На строго сопоставимых полных прогонах обновлённого датасета `v4` лучше `v2` по итоговой
точности на один запрос: **49/51 (96,08%) против 48/51 (94,12%)**. Все ошибки учитываются
как промахи; в обоих выбранных прогонах ошибок predictor/contract нет, поэтому условная
`quality accuracy` runner-а совпадает с end-to-end accuracy.

Главный выигрыш `v4` — не эти 1,96 п.п., а переход с 265 попарных сравнений и 13 вызовов
resolver-а на **один совместный вызов на QUERY**. Число model calls снизилось с 278 до 51,
p50 — с 12,77 до 4,63 с, p95 — с 49,74 до 7,42 с, стоимость — с $0,1263 до $0,0869.

Улучшение качества целиком обеспечено одним кейсом `q-000023`: `v2` превратил невидимого
на кропе производителя в отрицательный факт и дал `not_found`, а `v4` выбрал правильное
вино относительным сравнением всей группы. В остальных 50 случаях итоговые ответы версий
совпали. Поэтому текущий прогон подтверждает эффективность архитектуры по latency/cost, но
ещё не доказывает устойчивое улучшение accuracy.

У `v4` есть критическая функциональная регрессия: схема разрешает выбрать только один slug
из группы и вообще не содержит `not_found`. Единственный текущий `not_found`-кейс
`q-000050` поэтому **невозможно** решить правильно. Потолок этой реализации на датасете —
50/51 (98,04%). Кроме того, текстовый checklist больше не связан валидатором с решением:
в `q-000050` модель сама пишет `BRUT` у QUERY и `Extra Brut` у выбранного ELEMENT, но всё
равно выбирает ELEMENT, и контракт принимает противоречивый ответ.

`q-000047` — не ошибка gold. На QUERY и правильном Эталоне читается `ПОЛУСУХОЕ БЕЛОЕ`,
но обе версии выбрали `СУХОЕ БЕЛОЕ`. Это OCR/semantic failure на минимальном различителе.

Остающиеся различия, кроме собственно алгоритма:

- generation seed провайдеру не задан; `temperature=0` не гарантирует побитовую
  детерминированность внешнего VLM;
- `v2` в source допускает до пяти retry на HTTP 429, `v4` — ноль. В этих двух прогонах
  ветка retry не сработала, поэтому на измеренный результат не повлияла;
- прогоны выполнены последовательно с разницей примерно в три минуты, поэтому состояние
  внешнего сервиса не контролируется полностью.

### Почему не взят старый v4 с 50/51

В `ndr/results/v4/20260919T182203.570381Z` действительно записано 50/51, но это **не тот же
evaluation input**, несмотря на те же 51 изображения, одинаковые counts и одинаковые hashes
трёх исходных CSV в `dataset_metadata`.

Сопоставление lossless cases по SHA QUERY показало:

- у двух изображений изменён `expected_slug`, включая исправление нынешнего
  `q-000050` с catalog slug на `not_found`;
- у семи запросов изменён `candidate_order`;
- вследствие пересборки сдвинулись `query_id`;
- timeout был 180 с вместо 60 с;
- source fingerprint отличается, хотя runtime predictor и prompts совпадают; изменён
  `config.py`.

Порядок кандидатов для `v4` материален: prompt прямо предписывает при неразличимости брать
первый ELEMENT. Для Millstream старый прогон выбирал первым полусухое при порядке
`[полусухое, сухое]`, а обновлённый — сухое при порядке `[сухое, полусухое]`. Аналогично
другой запрос пары перевернулся в противоположную сторону. Поэтому старое 50/51 нельзя
предъявлять как результат `v4` на обновлённом датасете.

Это также обнаруживает дефект воспроизводимости runner-а: `run.json` хранит hashes исходных
CSV, но не fingerprint фактических `manifest.jsonl`, `groups.jsonl`, `catalog.jsonl`,
`excluded.jsonl`, `metadata.json` и версии `build_dataset.py`. Две фактически разные сборки
могут выглядеть одинаковыми по `dataset_metadata`.

### Остальные служебные артефакты

- `v2/20260919T202719.552189Z`: 51/51 predictor errors,
  `model is required: pass --model or set OPENROUTER_MODEL`; model calls 0, cost 0. Это
  preflight/configuration failure до платных запросов, а не quality run. Он не скрыт и не
  включён в знаменатель основного сравнения.
- `v4/20260919T193631.885778Z`: stale `running`, завершено 0/51, `metrics.json` отсутствует.
- Прогоны на одном кейсе являются smoke-тестами и не используются для оценки качества.
- Старые полные `v2/20260919T161641.983237Z` и `v4/20260919T182203.570381Z` относятся к
  предыдущей сборке cases; у обоих обнаружено семь несовпадений evaluation input с текущей.

### Метрика `not_found`

В gold есть один `not_found` — `q-000050`.

- `v2` выдал один `not_found`, но на catalog-кейсе `q-000023`; precision `not_found` = 0/1,
  recall = 0/1. На настоящем `not_found` он вернул catalog slug.
- `v4` не выдал ни одного `not_found`; recall = 0/1, precision не определена. Это не только
  поведение модели: `nearest_output_model` перечисляет в enum лишь candidate slugs.
- Catalog-only accuracy: `v2` 48/50 = 96%, `v4` 49/50 = 98%.

Сокращение числа формальных промахов с трёх до двух равно 33,3%, но это один discordant case
из 51. Двусторонний exact McNemar для единственного расхождения не даёт статистического
подтверждения преимущества. Нужны дополнительные фиксированные QUERY, а не повтор того же
платного прогона.

## Что именно изменено в v4

### v2: compare each, затем resolve

Для каждого QUERY `v2`:

1. отдельно сравнивает QUERY с каждым ELEMENT;
2. возвращает строгое `same/different` по maker/profile и, при непустом vintage, year;
3. Pydantic-validator требует согласия `verdict` со всеми bool-флагами;
4. при нуле `same` возвращает `not_found`;
5. при одном `same` возвращает его slug;
6. при нескольких `same` делает отдельный resolver call.

На обновлённом датасете это дало 265 comparison calls и 13 resolver calls. Диагностика
первой стадии относительно gold:

| Показатель | Значение |
|---|---:|
| True positive candidate verdicts | 49 |
| False negative candidate verdicts | 1 |
| False positive candidate verdicts | 18 |
| True negative candidate verdicts | 197 |
| Precision `same` | 73,13% |
| Recall `same` | 98,00% |
| F1 `same` | 83,76% |
| QUERY с 0 / 1 / >1 matches | 1 / 37 / 13 |
| Resolver correct | 12/13 |

Главная архитектурная проблема `v2`: сравнения независимы и охотно называют несколько
очень похожих товаров `same`. Resolver нужен на 25,49% QUERY, а последовательное число
удалённых вызовов растёт вместе с размером семейства.

### v4: one-shot joint selection

`v4` передаёт QUERY, все ELEMENT, все карточки и отдельную year-policy каждого ELEMENT в
одном запросе. Dynamic Pydantic enum разрешает вернуть только один slug из текущей группы.
Отдельных binary verdict и resolver нет.

Это напрямую объясняет основной operational gain:

- ровно 51 model call вместо 278;
- модель видит различия кандидатов одновременно, что исправило `q-000023`;
- latency больше не складывается из N последовательных вызовов внутри одного QUERY;
- исчезает стохастическая вторая стадия resolver-а.

Цена упрощения:

- `not_found` невозможен;
- нет candidate-level verdict, поэтому нельзя посчитать FP/FN первой стадии;
- checklist содержит только свободный `observation`, без `match/conflict/unknown`;
- schema проверяет принадлежность slug группе, но не согласованность evidence и выбора;
- при неразличимости prompt намеренно создаёт зависимость от первого ELEMENT;
- один запрос тяжелее: в среднем 5 691 total tokens против 2 239 у одного вызова `v2`
  (+154,1%). Для family rerank это приемлемо, для всех 2103 позиций Каталога — нет.

Таким образом, эксперимент меняет одновременно pipeline, prompt, output schema и retry
policy. Latency causal effect очевиден из сокращения calls, но вклад каждого изменения в
accuracy этим прогоном изолировать нельзя.

### `q-000023`: реальное улучшение v4

QUERY является крупным кропом лицевой этикетки: читаются `№2 Cuvée`, `Blanc de Noirs` и
иллюстрации, но neck label с `cock t'est belle` не попал в кадр. `v2` требует положительного
maker у каждого отдельного кандидата и отвергает даже точное визуально-текстовое совпадение.

`v4` одновременно видит №2 Blanc de Noirs, №5 Rosé и №1 Blanc de Blancs. Отсутствие maker
перестаёт быть фатальным: конкретные номер, название и дизайн однозначно отделяют №2 от двух
соседей. Это подтверждает основную гипотезу joint rerank для частично видимой этикетки.

### `q-000047`: gold корректен, обе версии ошибаются

Ручная сверка QUERY и обоих Эталонов показывает:

- на QUERY под `МОЛОДОЕ` напечатано `ПОЛУСУХОЕ БЕЛОЕ`;
- правильный Эталон и карточка также полусухие, сорт Мускат;
- выбранный неправильный Эталон — `СУХОЕ БЕЛОЕ`, сорт Алиготе.

Это не dataset/gold inconsistency. Нужен нативный crop строки сахара и отдельное OCR/evidence,
а не ещё одно глобальное сравнение бутылок. Старые lossless cases дополнительно показывают,
что one-shot `v4` меняет выбор вместе с первым ELEMENT для двух Millstream QUERY.

### `q-000050`: обновлённый gold корректен

На QUERY ясно видны `PRIMUM ALVEUS`, `BLANC DE BLANCS`, `BRUT`, `2019`, `IV`. Ближайший
catalog ELEMENT совпадает по линейке, году и оформлению, но на нём напечатано `EXTRA BRUT`.
Это отдельная товарная позиция; нужного `BRUT 2019 IV` среди кандидатов нет. `not_found`
обоснован, а старый gold, считавший Extra Brut правильным ответом, был исправлен.

У `v2` рост близок к ожидаемому для последовательных pairwise calls. У `v4` размер группы
увеличивает payload, но не число сетевых round trips, поэтому p50 остаётся в диапазоне
примерно 4,3–6,6 с.

Относительно продуктового SLA:

- `v2`: 0/51 QUERY ≤3 с, 33/51 >10 с;
- `v4`: 2/51 QUERY ≤3 с, 51/51 ≤10 с;
- `v4` проходит жёсткий десятисекундный предел этого isolated run, но p50 4,63 с всё ещё
  нарушает целевой SLA `<3 с`, причём сервисные накладные расходы здесь не добавлены.

Joint VLM следует оставить только для короткого ambiguous tail после локального retrieval и
OCR. Использовать его по всему Каталогу нельзя: число изображений и prompt size всё равно
растут линейно с числом кандидатов.

## Tokens и стоимость

Сокращение calls на 81,65% уменьшило total tokens лишь на 53,38%, потому что каждый запрос
`v4` содержит всю группу. Стоимость снизилась ещё слабее — на 31,22%.

Причина видна в cache accounting:

- `v2`: 584 500 prompt tokens, из них 321 920 cached; условно uncached 262 580;
- `v4`: 280 786 prompt tokens, из них лишь 29 568 cached; условно uncached 251 218;
- uncached prompt volume снизился только на 4,33%; prompt cost — с $0,08070552 до
  $0,075542808, то есть на 6,40%;
- основной денежный выигрыш дал completion cost: $0,0456192 → $0,0113388 (−75,14%).

Следовательно, `v4` уже заметно дешевле, но дальнейший cost gain надо искать в уменьшении
изображений/карточек после deterministic shortlist, а не только в сокращении числа HTTP calls.

## Основные проблемы

### 1. `not_found` сломан контрактом v4

`nearest_output_model` строит enum только из candidate slugs, а prompt требует обязательно
выбрать ELEMENT. Unit-тест `test_predict_makes_one_selection_call_and_always_returns_a_candidate`
закрепляет это как ожидаемое поведение. Для регулярного режима «товара нет в Каталоге» такая
архитектура непригодна.

### 2. Evidence не управляет решением

В `v2` bool-флаги и verdict связаны validator-ом. В `v4` остаются только три свободных строки
maker/profile/year и slug. Поэтому явный конфликт `BRUT` ↔ `EXTRA BRUT` проходит валидацию.
Нужны структурированные observed values и состояния `match/conflict/unknown/not_applicable`,
а выбор должен проверяться детерминированным кодом.

### 3. Короткие SKU-различители читаются нестабильно

`ПОЛУСУХОЕ`/`СУХОЕ`, `BRUT`/`EXTRA BRUT`, сорт и винтаж занимают малую часть этикетки.
Глобальный VLM иногда уверенно галлюцинирует значение, даже когда правильный вариант есть
в карточке и на Эталоне. Нужны label crop в нативном разрешении и отдельный OCR-канал.

### 4. First-candidate bias

Prompt разрешает выбирать первый ELEMENT при равных доказательствах. На Millstream смена
порядка переворачивает ответ. Seed 0 не защищает от этого, если при пересборке меняется базовый
порядок группы или query IDs. Candidate order должен быть стабильным, записанным в fingerprint,
а качество надо проверять отдельным новым экспериментом на permuted order, не retry того же
кейса.

### 5. Dataset fingerprint неполон

Текущая metadata не различает старую и обновлённую сборку при изменении build logic, gold и
candidate order. Это позволяет случайно сравнить 50/51 со старого датасета с 48/51 нового.
Runner должен сохранять hashes всех материализованных dataset-файлов и `build_dataset.py`,
а лучше единый canonical dataset fingerprint.

### 6. v4 всё ещё не выполняет SLA `<3 с`

One-shot устранил катастрофический p95 `v2` и уложил все запросы в 10 с, но только 2/51
уложились в 3 с. Remote VLM нельзя оставлять в обязательном критическом пути каждого QUERY.

### 7. Accuracy gain пока хрупкий

Только один из 51 ответа изменился между текущими версиями. Это хороший целевой фикс
`unknown maker`, но слишком мало для общего вывода о качестве. Дополнительно v4 теряет
candidate-level телеметрию, из-за чего aggregate accuracy хуже объясняет будущие регрессии.

## Рекомендация для следующей версии

Сохранить one-shot family rerank как основную гипотезу, но вернуть безопасный отказ и
структурированное evidence. Не смешивать это с заменой модели или provider route.

Предлагаемый минимальный эксперимент относительно immutable `v4`:

1. Расширить dynamic enum значением `not_found`.
2. Для различителей `maker`, `product_name`, `line_variant`, `grape`, `color`, `sweetness`,
   `carbonation`, `vintage` вернуть `observed_query`, `observed_candidate` и состояние
   `match/conflict/unknown/not_applicable`.
3. Явный conflict по году, sugar, сорту или line variant не должен компенсироваться общим
   визуальным сходством. `unknown maker` не должен быть conflict — это сохраняет фикс
   `q-000023`.
4. Разрешать catalog slug только при отсутствии hard conflict и достаточном положительном
   evidence; иначе `not_found`/ambiguous.
5. Перед joint rerank подавать нативный crop этикетки и OCR коротких различителей.
6. Убрать правило «при равенстве первый ELEMENT» либо возвращать ambiguity; отдельно новым
   immutable run проверить фиксированную перестановку candidate order.
7. Не возвращать remote VLM в путь всех 2103 карточек: сначала локальные CV/OCR retrieval и
   family shortlist, затем максимум один joint call для действительно неоднозначных случаев.

Целевые критерии следующего эксперимента:

- сохранить исправление `q-000023`;
- исправить `q-000047` и `q-000050`;
- получить минимум 50/51 при рабочем `not_found`, а не за счёт принудительного catalog slug;
- оставить один model call на ambiguous QUERY;
- не допустить contract/predictor errors и retry;
- отдельно публиковать end-to-end accuracy с errors как misses, conditional quality,
  `not_found`, latency, calls, tokens и cost.
